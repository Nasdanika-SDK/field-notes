[.lead]
In EMF, a contained object can be in a different resource from its container, and each object can be
placed separately. This is called containment proxies, or cross-resource containment, and it is off
by default, which is why the opposite is widely believed.

== The belief

Three beliefs about EMF resources are common, and all three are reasonable:

* A contained object is always in its container's resource. To save an object in a file of its own,
  it has to be a root of that file, referred to by a non-containment reference.
* If a contained object was saved in another file, then loading resolves the reference and the
  object moves into its container's resource, so the next save writes it inline.
* A contained object saved in a file of its own cannot know its container when its file is loaded
  alone, because its file is a file like any other.

The first is true by default. The second is not true at all. The third is true only when the
containment has no opposite, as this note shows.

== The answer

A containment reference whose `resolveProxies` is true, written `contains resolving` in Xcore, lets
a contained object live in a resource of its own. The object keeps its container: `eContainer()` is
the parent, and `eResource()` is the object's own resource, not the parent's.

* **Saving** writes a reference in the parent's file, `<children href="child.xmi#/"/>`, and the
  child in its own file.
* **Loading** is lazy. The parent's file loads with a proxy in place of the child, and the first
  access loads the child's file and replaces the proxy.
* **Resolving does not move the child.** It stays in its own resource, and saving the parent writes
  the reference again.
* **Placement is per object.** Adding a contained object to another resource's contents splits it
  out; removing it from its resource's contents moves it back into its container's resource.
* **A container reference records the container.** When the containment has an opposite, a
  container reference such as `parent`, the child's file refers back to the parent's file, and a
  child loaded alone has its container, as a proxy that the first access resolves. Without an
  opposite, the child's file has nothing about its container.

Without `resolveProxies`, which is the default for containment, the first belief holds, and the
same operations do something else: adding a contained object to a resource's contents removes it
from its container.

== Consequences

* **Several files to save.** Saving the parent's resource does not save the child's. Save every
  modified resource in the resource set.
* **References are relative.** The `href` is relative to the parent's file, so moving files means
  saving the parents again.
* **A file left behind.** When a child moves back into its container's resource, its old resource
  is empty and its file remains on disk with the old copy. Save the empty resource or delete it with
  `Resource.delete(...)`.
* **`eResource()` is not the root's resource.** Code that assumes that everything under a root is in
  the root's resource breaks: for example, a check that `eResource() == root.eResource()`, or saving
  only the root's resource.
* **Iteration loads.** `Resource.getAllContents()` and `eAllContents()` load the children's files
  as they go. That is what a walk over a whole model wants, and not what a quick look at one file
  wants. `EcoreUtil.getAllProperContents(resource, false)` loads nothing, but returns unresolved
  proxies, which the caller must expect.
* **A child read alone has no container, unless the containment has an opposite.** Without one, a
  tool that opens a child's file directly sees a root. With one, it sees a root that has a
  container, and code that takes a root of a resource to be a root of the model breaks.
* **Reading a container reference can load a file.** With a resolving container reference, so does
  `eContainer()`, which resolves either way: walking up from a child loads its ancestors' files.
  `eGet(feature, false)` reads the proxy without loading.
* **Without containment proxies, adding is moving.** Adding a contained object to a resource's
  contents silently detaches it from its container.

== A rule

A containment whose objects may be in files of their own works the same from either end when it has
three things:

* **`contains resolving`**, and the GenModel's `containmentProxies` for generated code (next
  section), so that a contained object can be in a file of its own.
* **A container reference as its opposite**, so that the object's file names its container. Without
  one, a file loaded alone forgets where its object belongs.
* **`container resolving`**, so that reading the container reference returns the container, the
  same as `eContainer()`, and not a proxy.

The cost is in the consequences above: more files to save, and loading that follows references in
both directions.

== Generated code

The tests use a dynamic metamodel, where `resolveProxies` on the reference is all it takes.
Generated code also needs the GenModel's `containmentProxies` attribute set to `true`; it is
`false` by default. The generator treats a containment reference as resolving only when both are
true. In Xcore:

[source]
----
@GenModel(containmentProxies="true")
package org.example.tree

class Node {
	String name
	contains resolving Node[] children opposite parent
	container resolving Node parent opposite children
}
----

The generated getter of a container reference returns `null` unless the object is contained
through the reference's opposite. Otherwise it returns `eContainer()`, which resolves, when the
reference is resolving, and `eInternalContainer()`, which does not, when it is not.

This section comes from reading EMF, not from a test, because the notes do not generate code yet:

* `GenFeatureImpl.isResolveProxies()` in `org.eclipse.emf.codegen.ecore` 2.46.0 checks
  `GenModel.isContainmentProxies()` and `EReference.isResolveProxies()`.
* The getter's body is in the generator's `templates/model/Class.java`, in the same artifact.
* The Xcore grammar in `org.eclipse.emf.ecore.xcore` 1.38.0 accepts `contains resolving` and
  `container resolving`; without `resolving`, neither resolves proxies.
